BeProduct Style -> DTC field mapping (interested fields)
========================================================
Verified live against the BeProduct "KTB" folder schema on 2026-06-17
(api.style.folder_schema / folder_colorway_schema, folder id
37dcc63a-4754-4bb8-8d34-8c07a4145fcd).

Stage numbers below (00, 20, 20b, 40, 45, 50, 55) are the v2 stages in
docs/PIPELINE.md. Direction, keys and the PATCH allow-list are owned by
docs/SYNC_CONTRACT.md; this file owns DTC column names, fieldIds and JSONPaths.

Phase 6 structural update (2026-06-26):
  - header_number field renamed in BP from "LF Style Number" → "BP Style Number".
    The field_id (header_number) and data values are UNCHANGED.
  - New BP field lf_style_number (name "LF STYLE NUMBER"): separate from header_number.
    Will be populated by upstream integration; currently empty for most styles.
    Feeds the EXISTING DTC "LF Style#" column (NOT a new DTC column).
  - New BP field brand_hk (name "Brand"): single-value brand string used in the
    composite key. Replaces brands_multi ("BRANDS") in the key. Ignore field_id 'brand'
    (old BRAND field, single-value legacy, not to be confused with brand_hk).
  - Composite key target: [Customer, BP Style# (header_number), SeasonCode, Brand (brand_hk)]
  - In-request row match key target: ("BP Style#", "Color / Wash")
  - NO new BeProduct "Legacy Code" field. The existing customer_style_number field
    (CUSTOMER STYLE NUMBER / PLM #) is what DTC calls "Legacy Code". Populated by
    upstream integration; flows BP→DTC optional (was DTC→BP before Phase 6).
  - DTC "Customer Style#" column: DECIDED NOT TO CREATE (2026-07-02). No DTC→BP
    path for customer_style_number. Removed from phase2.REVERSE_HEADER_FIELDS.
  - "BP Style#" DTC column: LIVE (was pending in 2026-07). Holds header_number
    (BP Style Number) and is the in-request match key with "Color / Wash".

JSONPath conventions (against a Style record from api.style.attributes_list):
  - Header fields live in an ARRAY: headerData.fields[] = [{id, name, type, value}, ...]
    Select by the stable fieldId, e.g.   headerData.fields[id="style_status"].value
    (Prefer id over name: names are inconsistently cased and some have trailing
    spaces, e.g. "CUSTOMER STYLE NUMBER / PLM #".)
  - Colorway fields live in a MAP keyed by fieldId, one per colorway:
    colorways[].fields.<fieldId>
    (colorName is a top-level colorway property, not inside .fields.)
  - frontImage is a header-level object: headerData.frontImage.origin


Sync direction: see docs/SYNC_CONTRACT.md -> "Direction partition" (one-way per
field) and "The WIP sheetData PATCH allow-list". Summary of who writes what,
for reading the Notes column below:
  - BeProduct -> DTC style fields: transform (Stage 20) stages them, wip_push
    (Stage 40) writes them. Fabric Group / Mill Fabric Article # get INSERT-only
    "NO TPM BOM" sentinels; Color / Wash gets "NO BP COLORWAY" for a style
    with zero colorways.
  - TPM/BOM (Lakebase) -> DTC material fields (Fabric Group, Placement, Mill
    Fabric Article #, Content, LF Fabric ID): pull_bom (Stage 20b) + wip_push
    (Stage 40). NOT sourced from BeProduct.
  - Sample-app submit history -> DTC: Stage 20 formats, Stage 40 writes.
  - DTC -> BeProduct style: phase2_push (Stage 50).
  - Style Image: phase3_images (Stage 45), binary upload only.

Last-minute schema changes captured here (2026-06-17):
  1. BRANDS (and CUSTOMER) are MultiSelect lists of plain strings; with the
     one-selection setup guarantee, read value[0] (not value[0].value).
     Match by fieldId (brands_multi / sold_to_customer), not by display name.
  2. "Lot Code" moved to the COLORWAY schema as fieldId "drawing_number_walmart"
     (colorways[].fields.drawing_number_walmart). It is filled by the DTC->BeProduct
     Stage 50 push, hence empty in BeProduct unless DTC holds a value. The old header-level "Lot Code" is
     deprecated and must not be read.

Phase 6 changes (2026-06-26, validated live):
  3. header_number field RENAMED from "LF Style Number" to "BP Style Number" in
     BeProduct. Field_id and data values unchanged. The old ktb_styles column
     "lf_style_number" (populated from header_number) is renamed to "bp_style_number".
  4. New BeProduct field: lf_style_number (field_id "lf_style_number", name "LF STYLE
     NUMBER"). Separate from header_number. Currently empty for most styles; will be
     populated by upstream integration. Pushed optionally to EXISTING DTC "LF Style#".
  5. New BeProduct field: brand_hk (field_id "brand_hk", name "Brand"). Single-value
     string. Used as the Brand in the composite key. brands_multi ("BRANDS") was
     retained in ktb_styles for reference at the time — REMOVED entirely 2026-09-03
     (owner spec: "take out 'brands' from BP tables — use 'brand' (brand_hk) only
     now"); no longer extracted into ktb_styles/staging at all. See AGENTS.md
     decisions log.
  6. NO new BeProduct "Legacy Code" field. The existing customer_style_number
     (CUSTOMER STYLE NUMBER / PLM #) is the "Legacy Code" source. It will be populated
     by upstream integration; flows BP→DTC (was DTC→BP before Phase 6).
   7. DTC "Customer Style#" column: DECIDED NOT TO CREATE (2026-07-02). Removed from
      phase2.REVERSE_HEADER_FIELDS. No DTC→BP for customer_style_number.
   8. DTC "BP Style#" column: LIVE. BP→DTC, carries header_number; the in-request
      match key with "Color / Wash".
   9. Terminal Product Status ("Finalized" / "Drop"): ktb_styles KEEPS these styles
      (they only skip sample-app enrichment in p1p7_beproduct_style_sync.py). The
      transform (Stage 20) lets one last push through so the terminal status itself
      reaches DTC, then excludes the style once the WIP row's own Product Status has
      caught up. A reactivated style resumes automatically. Logic: sync/lifecycle.py.
  10. DTC column "Gender": LIVE. BP→DTC from BP field_id `gender`. Values:
      Ladies/Mens/Girls/'' (confirmed live). In FIELD_MAPPING + INTERESTED_FIELDS.

      never overwrites existing DTC values (DEFAULT_FILL_COLS in phase1). Staged as
      lit("Supplier") in transform. Not sourced from any BeProduct field.
  12. The PATCH allow-list is wip_plan.allowed_patch_columns() (derived from the
      payload builders) -- see docs/SYNC_CONTRACT.md. Column existence is checked
