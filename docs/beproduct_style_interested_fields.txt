BeProduct Style -> DTC field mapping (interested fields)
========================================================
Verified live against the BeProduct "KTB" folder schema on 2026-06-17
(api.style.folder_schema / folder_colorway_schema, folder id
37dcc63a-4754-4bb8-8d34-8c07a4145fcd).

Phase 6 structural update (2026-06-26):
  - header_number field renamed in BP from "LF Style Number" → "BP Style Number".
    The field_id (header_number) and data values are UNCHANGED.
  - New BP field lf_style_number (name "LF STYLE NUMBER"): separate from header_number.
    Will be populated by upstream integration; currently empty for most styles.
    Feeds the EXISTING DTC "LF Style#" column (NOT a new DTC column).
  - New BP field brand_hk (name "Brand"): single-value brand string used in the
    composite key. Replaces brands_multi ("BRANDS") in the key. Ignore field_id 'brand'
    (old BRAND field, single-value legacy, not to be confused with brand_hk).
  - Composite key target: [Customer, BP Style# (header_number), SeasonCode, Brand (brand_hk)]
  - In-request row match key target: ("BP Style#", "Color / Wash")
  - NO new BeProduct "Legacy Code" field. The existing customer_style_number field
    (CUSTOMER STYLE NUMBER / PLM #) is what DTC calls "Legacy Code". Populated by
    upstream integration; flows BP→DTC optional (was DTC→BP before Phase 6).
  - DTC "Customer Style#" column: DECIDED NOT TO CREATE (2026-07-02). No DTC→BP
    path for customer_style_number. Removed from phase2.REVERSE_HEADER_FIELDS.
  - "BP STYLE#" (new DTC column, PENDING): will hold header_number (BP Style Number).
    This is the new in-request match key once created. Until then MATCH_KEY_COLS is
    set to ("BP Style#", ...) in code but will fail to match until column exists and
    DTC admin migrates "LF Style#" data into "BP Style#".

PENDING DTC column creation (as of 2026-07-02, confirmed by scanning all 75 active KTB requests):
  - "BP Style#"  — BLOCKER for match key switch; sync produces missing_bp_style until created
  - "Gender"     — dormant Phase 1 mapping until created
  - "Supplier"   — dormant Phase 1 default-fill until created
  NOT PENDING (already exist in the view, just blank on some/older requests):
  - "Legacy Code", "Garment Finish", "Tech Pack Stage", "Main Vendor (Sampling)"
  NOTE: DTC "Customer Style#" is NOT being created (decision 2026-07-02).
  NOTE: GET /v1/views/{viewId} returns 403 for the sync API key (confirmed for all view IDs
  including the document-level template 6a3907f6df772fd797ee5b7c). Per-request view ID used
  for sheet data access remains 69f04983501f3d9cf4fc379c. Since the view definition endpoint
  is inaccessible, allowed_cols uses a data-scan union with FALLBACK_COLS so Phase-1-owned
  columns are always sent even when blank on a fresh sheet.

JSONPath conventions (against a Style record from api.style.attributes_list):
  - Header fields live in an ARRAY: headerData.fields[] = [{id, name, type, value}, ...]
    Select by the stable fieldId, e.g.   headerData.fields[id="style_status"].value
    (Prefer id over name: names are inconsistently cased and some have trailing
    spaces, e.g. "CUSTOMER STYLE NUMBER / PLM #".)
  - Colorway fields live in a MAP keyed by fieldId, one per colorway:
    colorways[].fields.<fieldId>
    (colorName is a top-level colorway property, not inside .fields.)
  - frontImage is a header-level object: headerData.frontImage.origin

Sync direction (one-way per field; see AGENTS.md "field mapping" for code locations):
  BeProduct -> DTC (Phase 1, phase1.FIELD_MAPPING):
    Product Status, Style Description, Class, Sub Class, Division, Brand,
    Garment Finish, Tech Pack Stage, Gender (pending DTC col);
    BP Style# (new key; pending DTC col), LF Style# (optional), Legacy Code (optional);
    Supplier (default-fill "Supplier" when DTC cell blank; pending DTC col);
    Fabric Group, Placement (default-fill ONLY -- fixed 2026-09-03: these are
    Phase 10's fields now, sourced from TPM/BOM data, not BeProduct; Phase 1
    only sets the initial "MAIN MATERIAL CONTENT" placeholder on INSERT and
    NEVER re-pushes on UPDATE once the DTC cell holds any value -- a scheduled
    Phase 1 run was live-observed silently reverting Phase 10's real
    enrichment before this fix; see AGENTS.md decisions log)
  BeProduct -> DTC (Phase 7, sample-app submit history; sync.samples.format_sample_field):
    All 6 apps mapped (confirmed live 2026-08-28, 204-field WIP_ITS_USE view):
    Proto -> "Proto Sample - Sample Status", PreLine -> "Pre-line Sample - Status",
    SMS -> "SMS - Sample Status", Fit -> "2nd Fit Sample Approval Status" (was
    "1st Fit Sample Approval Status" before the 2026-08-28 DTC WIP restructure),
    PP -> "PP Sample Submission Approval Status" (was "2nd Fit Sample Approval
    Status"; requested name "PP Sample Approval Status" does not exist live -
    confirmed correct by the project team 2026-08-28), TOP -> "TOP Sample
    Approval Status".
    Value = one quoted comma-separated line PER submit: "name","status","date"
    (NOT a JSON array - no brackets at all), multiple submits stacked on
    separate newline-separated lines (confirmed 2026-08-28; superseded an
    earlier same-day flat-JSON-array iteration, itself a fix of the original
    nested [[ ]] array). phase1.norm() preserves embedded newlines (changed
    2026-08-28) so the multi-line structure survives to the DTC push.
  DTC -> BeProduct (Phase 2, phase2.REVERSE_*):
    Lot#, Main Vendor (Sampling), Main Factory (Sampling),
    Main Factory Customer ID (no BeProduct target yet -> skipped)
  [REMOVED Phase 6]: "Legacy Code" DTC→BP. "Customer Style#" DTC column not created.
  key (used for matching, not overwritten): BP Style# + Color / Wash (in-request);
    [Customer, BP Style#, SeasonCode, Brand] (composite/request-routing)
  BeProduct -> DTC image only (Phase 3, phase3 / p3_beproduct_to_dtc_images):
    Style Image (binary; uploaded via the multipart images endpoint, only when
    the DTC cell is blank and BeProduct has a valid front_image_url. NEVER
    pushed via the Phase 1 sheetData PATCH, and never read back to BeProduct.)

Last-minute schema changes captured here (2026-06-17):
  1. BRANDS (and CUSTOMER) are MultiSelect lists of plain strings; with the
     one-selection setup guarantee, read value[0] (not value[0].value).
     Match by fieldId (brands_multi / sold_to_customer), not by display name.
  2. "Lot Code" moved to the COLORWAY schema as fieldId "drawing_number_walmart"
     (colorways[].fields.drawing_number_walmart). It is filled by the DTC->BeProduct
     Phase 2 push, hence empty in BeProduct now. The old header-level "Lot Code" is
     deprecated and must not be read.

Phase 6 changes (2026-06-26, validated live):
  3. header_number field RENAMED from "LF Style Number" to "BP Style Number" in
     BeProduct. Field_id and data values unchanged. The old ktb_styles column
     "lf_style_number" (populated from header_number) is renamed to "bp_style_number".
  4. New BeProduct field: lf_style_number (field_id "lf_style_number", name "LF STYLE
     NUMBER"). Separate from header_number. Currently empty for most styles; will be
     populated by upstream integration. Pushed optionally to EXISTING DTC "LF Style#".
  5. New BeProduct field: brand_hk (field_id "brand_hk", name "Brand"). Single-value
     string. Used as the Brand in the composite key. brands_multi ("BRANDS") is retained
     in ktb_styles for reference but is no longer the key field.
  6. NO new BeProduct "Legacy Code" field. The existing customer_style_number
     (CUSTOMER STYLE NUMBER / PLM #) is the "Legacy Code" source. It will be populated
     by upstream integration; flows BP→DTC (was DTC→BP before Phase 6).
   7. DTC "Customer Style#" column: DECIDED NOT TO CREATE (2026-07-02). Removed from
      phase2.REVERSE_HEADER_FIELDS. No DTC→BP for customer_style_number.
   8. DTC "BP Style#" (NEW COLUMN, PENDING): BP→DTC, carries header_number value; new
      in-request match key once created. Code already writes to this column; sync will
      fail to match existing rows until DTC creates column and migrates data from "LF Style#".
   9. BeProduct styles with Product Status = "Finalized" are EXCLUDED from DTC sync
      (filtered in p1p7_beproduct_style_sync.py before app enrichment). Valid sync statuses:
      Proto, Pre-Line, SMS, Production (any status not equal to "Finalized").
  10. New DTC column "Gender" (PENDING): BP→DTC from BP field_id `gender`. Values:
      Ladies/Mens/Girls/'' (confirmed live). Code staged in FIELD_MAPPING + INTERESTED_FIELDS.
  11. New DTC column "Supplier" (PENDING): default-fill "Supplier" when DTC cell blank;
      never overwrites existing DTC values (DEFAULT_FILL_COLS in phase1). Staged as
      lit("Supplier") in transform. Not sourced from any BeProduct field.
  12. DTC view definition GET /v1/views/{viewId} returns 403 for all view IDs with the
      current sync API key (confirmed 2026-07-02, including document-level template
      6a3907f6df772fd797ee5b7c and per-request view 69f04983501f3d9cf4fc379c). The
      allowed_cols fallback now UNIONs the data-scan result with FALLBACK_COLS so
      Phase-1-owned columns that are blank on a fresh sheet are still allowed in PATCH.
