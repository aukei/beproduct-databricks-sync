Costing Chart — field mapping & data sources (Phase 9a)
=========================================================
Confirmed live against DTC UAT 2026-07-17.

This is the field-level SSOT only. For DAG placement, the 3-job split,
NT Orbit auth, cache mechanics, and every current gating condition, see
docs/PHASE9_WORKFLOW.md and docs/PIPELINE_GATES.md.

Purpose
-------
Phase 9a joins the DTC WIP master chart with the DTC LinePlan to produce a
denormalized "Costing Chart" at the Style × Color × Vendor/Factory slot level.
Output: `lft.beproduct.costing_chart` (full overwrite each run).

Input tables
------------
  lft.beproduct.dtc_wip_ktb        WIP rows (all fields in data_json)
  lft.beproduct.dtc_lineplan_ktb   LinePlan rows (all fields in data_json)

Join key
--------
  WIP  "Lineplan Ref #"  =  LinePlan  "Lineplan Ref #"
  NOTE: WIP column is plain "Lineplan Ref #" (no "(GC)" suffix — the spec
  annotation "(GC)" is not the literal DTC column name).
  INNER JOIN (changed from LEFT 2026-09-01, owner decision): a WIP row with
  a blank/unmatched "Lineplan Ref #" is dropped entirely, not surfaced with
  null LinePlan fields. The per-slot vendor-presence filter (below) still
  applies independently — a WIP row can match LinePlan and still produce
  zero costing rows if no vendor is assigned yet.

Vendor / Factory slot structure
--------------------------------
Each WIP row (style × color) produces up to 4 costing rows by transposing:

  supplier_type | vendor_col (WIP)           | factory_col (WIP)
  ──────────────┼────────────────────────────┼────────────────────────────────
  Main          | Main Vendor (Sampling)      | Main Factory (Sampling)
  1             | Vendor 1                   | Factory 1
  2             | Vendor 2                   | Factory 2
  3             | Vendor 3                   | Factory 3

Rows where the vendor column is blank are dropped.
A style × color may produce 1–4 costing rows.

CORRECTED 2026-09-01: the column carrying "Main"|"1"|"2"|"3" is named
`supplier_type` (was implemented as a separate `factory_slot` column,
initially confused with LinePlan's "INTERNAL/ SOURCED" field mapped to a
*different* `supplier_type` column — that was wrong). The original spec is
"Supplier Type - Generated from Master Chart data": ONE flag, generated from
WIP structure (which of the 4 vendor/factory column-pairs a row came from),
NOT LinePlan's "INTERNAL/ SOURCED" business classification. That LinePlan
value does not flow into costing_chart at all now.

LinePlan grouping note
-----------------------
LinePlan may have multiple rows per "Lineplan Ref #" (different colors / regions,
or -- per project team decision 2026-09-01 -- different requests, since LinePlan
requests have no naming-convention filter and ref# uniqueness across all of them
is a human-enforced invariant). The join uses the FIRST non-null value per ref#
for order_quantity / target_ldp / target_fob (Spark first() with ignorenulls=True).
p9a_build_costing_chart.py's LinePlan aggregation step also runs a best-effort
conflict DETECTOR (warns, does not block) when a ref's plan values actually
disagree across rows/requests.

Phase 9b — implemented, split into 2 notebooks / jobs (2026-09-03)
---------------------------------------------------------------
`dtc/notebooks/p9b_fill_duty_rates.py` (the notebook originally referenced
here) is now a superseded/manual-fallback artifact, kept for history but not
scheduled. Phase 9b runs as two independently-scheduled pieces:
  - `p9b1_compute_duty_rates.py` (job `BeProduct_DTC_sync_duty_compute`,
    task `compute_duty_rates`) -- NT Orbit lookups -> `costing_chart` only.
    Zero DTC dependency (no API key, no DTC read/write).
  - `p9b2_push_duty_to_wip.py` (main job `BeProduct_DTC_sync_dag`, task
    `push_duty_rates`) -- re-reads `costing_chart` for any row with a
    filled value and diffs against the live WIP row before PATCHing (only
    pushes fields that actually differ -- lean-PATCH, Ground Rule #6).
See `AGENTS.md`'s 2026-09-03 decisions log entry ("Pipeline split into 3
independent Databricks jobs") for the full rationale (DTC's concurrent-edit
limitation) and `docs/PIPELINE_GATES.md`'s "Phase 9b" section for the exact
current lookup/cache/push gating logic.

For costing rows where hts_code IS NULL or duty_rate_* IS NULL or tariff_rate IS NULL:
  1. Check the PERSISTENT cross-run cache table `duty_cache_table`
     (default lft.beproduct.nt_orbit_duty_cache; NEVER overwritten by Phase
     9a, unlike costing_chart) for a hit on
     (product_description, origin_country, import_country), fresh within
     `cache_ttl_days` (default 180). A hit is used directly — NO API call.
     Only a miss/stale entry calls the NT Orbit Duty Tools 3rd-party API
     (https://orbitduty.neotangent.com/API-DOCS/, POST /api/v1/calculate/single/,
     one call per market US/CA/MX still needed). This matters because each
     call is ~30s (sometimes longer — the connector's HTTP timeout is 60s,
     raised from 30s 2026-09-01 after live timeouts were observed) and
     costing_chart is FULLY OVERWRITTEN by every Phase 9a run (see below) —
     without a cache that survives ACROSS runs, every daily run would
     re-look-up every row from scratch. Calls are made SERIALLY by default
     (`parallel_calls`/`orbit_parallel_calls` job param = false) rather than
     via a thread pool, since NT Orbit's tolerance for concurrent calls under
     real load is unconfirmed; set `parallel_calls=true` (+ `max_workers`) to
     trade safety for throughput once that's validated.
  2. Fill in the values on costing_chart (write-once — never overwrites an
     already-populated cell). duty_rate_xx is taken from the response's
     "General Duty" detailed_line rate (NOT the combined data.duty_rate,
     which also includes tariff + fees); tariff_rate is the sum of any other
     type="duty" detailed_lines, and is only ever set from a US-market call.
     Newly-fetched results are also written into the persistent cache table
     so the NEXT run (even after Phase 9a wipes costing_chart) can reuse
     them without another API call.
  3. If push_to_wip=true, push updated HTS / Duty Rate values back to the
     corresponding per-slot WIP columns via the same Phase 1 PATCH contract
     (DTCConnector.patch_rows, UPDATE-only since the WIP rows already exist).
     Tariff Rate has NO live WIP column yet (see note above) so it is pushed
     to nowhere — it stays in costing_chart only; the push step logs this as
     a "skipped" reason rather than silently dropping the value.

Auth: NT Orbit requires a per-user Microsoft Entra ID delegated OAuth2 bearer
token (NOT the DTC x-api-key scheme) — refresh_token -> access_token via
dtc/python/client/entra_auth.py. One-time interactive setup:
scripts/nt_orbit_oauth_setup.py (run locally, once, as the delegated user).
Entra rotates the refresh_token on (most) uses; the notebook auto-persists
the rotated value to lft.<schema>.nt_orbit_oauth_state every run
(dbutils.secrets is read-only, so it cannot be written back to the secret
scope from a notebook) and prefers that table's value over the static secret
on every subsequent run — so, like BeProduct's OAuth, this is "seed once,
then fully automatic" as long as the job keeps running at least every ~90
days (it runs 3x/day). No manual secret-scope updates needed after the
initial seed.

Live in the deployed job as of 2026-09-01: `run_phase9b=true` gates the main
job's `push_duty_rates` task. `push_duty_to_wip` was REMOVED as a job
parameter 2026-09-08 (found redundant during a full-pipeline conflict scan
-- `run_phase9b` already gates the task's only job post-split, so the
separate flag had zero effect). The notebook's own standalone widget default
for `dry_run` remains `"true"` (safe for ad-hoc/interactive runs without job
parameters); the job's shared `dry_run` parameter is `false`.

Costing chart table name is a PARAMETER (widget/job-param `costing_chart_table`):
  default : lft.beproduct.costing_chart
  testing : lft.beproduct.costing_chart_kei
Persistent duty-lookup cache table + TTL are also PARAMETERS
(`duty_cache_table` / `cache_ttl_days`), default
lft.beproduct.nt_orbit_duty_cache / 180 days.
Pure decision logic (no Spark/HTTP) lives in dtc/python/sync/duty.py, unit
tested in dtc/tests/test_duty.py.

Completeness filter (Step 1b) — see docs/PIPELINE_GATES.md "Phase 9a" for

Costing chart key
------------------
  [customer, season_code, brand, bp_style_no, lf_style_no, color_name,
   lineplan_ref, material_no, supplier_type, supplier, factory]

`material_no` added 2026-09-03 (REVISED same day from an initial
`fabric_content` attempt -- owner correction: "multiple material_no can
have same content, and multiple style could share a lineplan" -- so
`fabric_content` and `lineplan_ref` are each individually unreliable
material-level discriminators; `material_no` -- Phase 10's own "Mill Fabric
Article #" -- is the real, unambiguous one). Phase 10 can produce multiple
WIP rows sharing the same lineplan_ref/bp_style_no/color_name/supplier/
factory (one "Main Fabric" row + one duplicate per "Fabric" segment),
differing only in material fields; without material_no in the key, Phase
9b's MERGE write-back could match multiple source rows to the same
costing_chart row. `p9b2_push_duty_to_wip.py`'s WIP-row lookup index uses
the identical (bp_style_no, color_name, material_no) key for the same
reason.

The table is FULLY OVERWRITTEN on every Phase 9a run (no incremental).
All prior Phase 9b-filled values are also overwritten; Phase 9b must re-run
after each Phase 9a rebuild to re-populate tariff_rate / HTS gaps.
