Costing Chart — field mapping & data sources (Stage 30, build_costing)
=====================================================================
Confirmed live against DTC UAT 2026-07-17; inputs revised for v2 (2026-09-15).

This is the field-level SSOT only. For DAG placement, every gate, the
duty_compute companion job (NT Orbit auth, cache mechanics, schedules) and
force_refresh_duty, see docs/PIPELINE.md -> "Stage 30 — build_costing" and
"Companion job". Exact DTC column names and the PATCH allow-list:
docs/SYNC_CONTRACT.md -> "Costing/duty → DTC". Symptoms ("no costing line",
"missing / outdated duty"): docs/TROUBLESHOOTING.md.

Purpose
-------
build_costing (p9a_build_costing_chart.py, wip_effective_mode=intent) joins
the WIP master chart with the DTC LinePlan to produce a denormalized
"Costing Chart" at the Style × Color × Material × Vendor/Factory slot level.
Output: `lft.beproduct.costing_chart` (full overwrite each run; recovery is
Delta time travel, `RESTORE TABLE … VERSION AS OF n`).

Who writes duty values:
  - BeProduct_DTC_sync_duty_compute (p9b1_compute_duty_rates, serverless,
    10:00 / 15:00 HKT) -- NT Orbit -> nt_orbit_duty_cache + costing_chart.
  - build_costing (Stage 30) -- refills duty fields from the WIP row and from
    nt_orbit_duty_cache on every rebuild (zero API calls).
  - wip_push (Stage 40, main job BeProduct_DTC_sync_v2) -- pushes HTS / duty /
    tariff from costing_chart to the per-slot DTC WIP columns below.

Input tables (v2 "intent" mode)
-------------------------------
  lft.beproduct.dtc_wip_ktb                WIP start-of-run snapshot (data_json) --
                                           base row + every DTC-OWNED column
                                           (Lineplan Ref #, vendor/factory slots,
                                           production country, existing HTS/duty/tariff)
  lft.beproduct.beproduct_to_dtc_staging   overlaid onto the WIP row: style
                                           identity, Class, Sub Class, Gender, ...
                                           (what wip_push is about to write)
  lft.beproduct.bom_segments               overlaid onto the WIP row: material_no,
                                           fabric_content, fabric_group
  lft.beproduct.dtc_lineplan_ktb           LinePlan rows (data_json)
  lft.beproduct.nt_orbit_duty_cache        read-only duty back-fill
  In the column table below, "WIP JSON" means the WIP column name; for the
  overlaid columns the value comes from staging / bom_segments in intent mode.

Join key
--------
  WIP  "Lineplan Ref #"  =  LinePlan  "Lineplan Ref #"
  NOTE: WIP column is plain "Lineplan Ref #" (no "(GC)" suffix — the spec
  annotation "(GC)" is not the literal DTC column name).
  INNER JOIN (changed from LEFT 2026-09-01, owner decision): a WIP row with
  a blank/unmatched "Lineplan Ref #" is dropped entirely, not surfaced with
  null LinePlan fields. The per-slot vendor-presence filter (below) still
  applies independently — a WIP row can match LinePlan and still produce
  zero costing rows if no vendor is assigned yet.

Vendor / Factory slot structure
--------------------------------
Each WIP row (style × color) produces up to 4 costing rows by transposing:

  supplier_type | vendor_col (WIP)           | factory_col (WIP)
  ──────────────┼────────────────────────────┼────────────────────────────────
  Main          | Main Vendor (Sampling)      | Main Factory (Sampling)
  1             | Vendor 1                   | Factory 1
  2             | Vendor 2                   | Factory 2
  3             | Vendor 3                   | Factory 3

Rows where the vendor column is blank are dropped.
A style × color may produce 1–4 costing rows.

CORRECTED 2026-09-01: the column carrying "Main"|"1"|"2"|"3" is named
`supplier_type` (was implemented as a separate `factory_slot` column,
initially confused with LinePlan's "INTERNAL/ SOURCED" field mapped to a
*different* `supplier_type` column — that was wrong). The original spec is
"Supplier Type - Generated from Master Chart data": ONE flag, generated from
WIP structure (which of the 4 vendor/factory column-pairs a row came from),
NOT LinePlan's "INTERNAL/ SOURCED" business classification. That LinePlan
value does not flow into costing_chart at all now.

WIP HTS / Duty / Tariff field names (exact DTC column names, confirmed 2026-07-17)
-- written by wip_push (Stage 40); part of the PATCH allow-list in
docs/SYNC_CONTRACT.md (executable: wip_plan.allowed_patch_columns()) --
--------------------------------------------------------------------------
  Main Factory HTS Code           Main Factory Duty Rate (US/CA/MX)
  Factory 1 - HTS code            Factory 1 - Duty Rate (US/CA/MX)
  Factory 2 - HTS code            Factory 2 - Duty Rate (US/CA/MX)
  Factory 3 - HTS code            Factory 3 - Duty Rate (US/CA/MX)

  Main Factory Tariff             Factory 1 - Tariff
  Factory 2 - Tariff              Factory 3 - Tariff

  ^ REVISED 2026-09-17, verified against the view definition (GET /v1/views/{id}
    -> dynamicFields, 205 columns). These names are NOT symmetric with the HTS /
    Duty ones above -- no "rate" suffix, and " - " on the numbered slots. The
    earlier entry here ("Main Factory Tariff rate", "Factory 1/2/3 - Tariff
    rate", NOT PRESENT as of 2026-07-17) was wrong on BOTH counts: the columns
    exist, and none of those names do. Source them from duty.WIP_TARIFF_COL,
    never by retyping -- a name absent from the view is dropped by wip_plan's
    allow-list and the value silently never lands.
    Check the VIEW DEFINITION, not the dtc_wip_* Delta snapshot: the snapshot
    only materialises columns that are POPULATED in sheetData, so an empty
    column looks like a missing one.

LinePlan field names (exact DTC column names — all UPPERCASE, confirmed 2026-07-17)
-------------------------------------------------------------------------------------
  "Lineplan Ref #"                join key to WIP
  "PROJECTED VOLUME (season)"     → order_quantity
  "TARGET SAP w/ Tariff impact"   → target_ldp     (lowercase 'i' in "impact")
  "TARGET FOB"                    → target_fob
  "INTERNAL/ SOURCED"             pulled into dtc_lineplan_ktb.internal_sourced but

  View: "Full" (id 69f0788555010bb745140ac4, 30 fields).
  No "LINEPLAN_ITS_USE" view exists in UAT; p9a_pull_lineplan_to_delta tries it first
  and falls back to "Full".

LinePlan grouping note
-----------------------
LinePlan may have multiple rows per "Lineplan Ref #" (different colors / regions,
or -- per project team decision 2026-09-01 -- different requests, since LinePlan
requests have no naming-convention filter and ref# uniqueness across all of them
is a human-enforced invariant). The join uses the FIRST non-null value per ref#
for order_quantity / target_ldp / target_fob (Spark first() with ignorenulls=True).
p9a_build_costing_chart.py's LinePlan aggregation step also runs a best-effort
conflict DETECTOR (warns, does not block) when a ref's plan values actually
disagree across rows/requests.

Duty lookup, cache, auth and push -- pointer
--------------------------------------------
Not duplicated here. See docs/PIPELINE.md:
  - "Companion job" -> BeProduct_DTC_sync_duty_compute: which markets need a
    call, cache TTL (cache_ttl_days, default 180), Entra delegated OAuth,
    "General Duty" line vs tariff lines, serial calls, the sequencing gap.
  - "Refreshing a duty rate that has CHANGED -- force_refresh_duty".
  - "Stage 30" gates 1-9: completeness filter (material_no, bp_style_no,
    fabric_content, fabric_group == "Main Fabric", all ANDed), LinePlan INNER
    JOIN, per-slot vendor filter, WIP fallback, cache fill.
  - "Stage 40" for the DTC push of duty values.
v1's separate duty-push task is superseded (folded into wip_push) and not
scheduled.

Parameters (field-relevant only)
--------------------------------
  costing_chart table : `costing_chart_table` / `costing_chart_table_name`,
                        default lft.beproduct.costing_chart (kept for future
                        comparison builds; the old costing_chart_kei scratch
                        table was dropped 2026-09-15)
  duty cache / TTL    : `duty_cache_table` / `cache_ttl_days`, default
                        lft.beproduct.nt_orbit_duty_cache / 180 days
Pure decision logic (no Spark/HTTP) lives in dtc/python/sync/duty.py, unit
tested in dtc/tests/test_duty.py.

Costing chart key
------------------
  duty.COSTING_KEY =
  [customer, season_code, brand, bp_style_no, lf_style_no, color_name,
   lineplan_ref, material_no, supplier_type, supplier, factory]
  Joins/MERGEs on it MUST be null-safe (<=> / eqNullSafe) -- lf_style_no can
  be NULL (see docs/PIPELINE.md Stage 30).

`material_no` added 2026-09-03 (REVISED same day from an initial
`fabric_content` attempt -- owner correction: "multiple material_no can
have same content, and multiple style could share a lineplan" -- so
`fabric_content` and `lineplan_ref` are each individually unreliable
material-level discriminators; `material_no` -- the BOM contribution's own "Mill Fabric
Article #" -- is the real, unambiguous one). The BOM fan-out produces multiple
WIP rows sharing the same lineplan_ref/bp_style_no/color_name/supplier/
factory (one "Main Fabric" row + one duplicate per "Fabric" segment),
differing only in material fields; without material_no in the key,
duty_compute's MERGE write-back could match multiple source rows to the same
costing_chart row. wip_push applies duty to every WIP row sharing
(style, colour, article) for the same reason.

The table is FULLY OVERWRITTEN on every build_costing run (no incremental).
Duty values survive the rebuild via the WIP fallback (all five fields,
including tariff_rate since 2026-09-17) and the nt_orbit_duty_cache fill --
duty_compute does NOT need to re-run after each rebuild.
